# Website Downloader (@WebsiteDownloaderBot) v1.10.0

Telegram bot (Node.js + Telegraf) that turns any website into an offline copy: every page, image and file, linked locally.
Send `example.com` (or a message that contains a link) -> get one or more ZIPs -> unzip ALL of them into the same folder -> open `index.html`.

Design rule: **advanced backend, simple UI.** Every decision (browser or not, stealth, retries, compression, resuming) is automatic; people only see outcomes.

## Deploy on Railway
1. Push this folder to a GitHub repo and create a Railway project from it (the `Dockerfile` is detected automatically).
2. In the same project click **+ New -> Database -> PostgreSQL**, then again for **Redis**.
3. On the bot service, add variables:
   - `BOT_TOKEN` = token from @BotFather
   - `DATABASE_URL` = `${{Postgres.DATABASE_URL}}`
   - `REDIS_URL` = `${{Redis.REDIS_URL}}`
   - `ADMIN_IDS` = your Telegram numeric ID (enables /stats, /ban, /unban, /block, /unblock)
4. Give the bot service at least 1 GB RAM (Chromium needs it) and run only ONE instance (long polling).
5. Optional: set the service health check path to `/health`.
6. Deploy. Tables are created automatically on first start. Logs show `Postgres: connected` and `Redis: connected`.

Postgres and Redis are optional: without them the bot still works (in-memory cache/limits, no history, no resume after restart).

## Configuration (`.env`)
The ZIP includes a ready-made **`.env`** (and an identical `.env.example`). Every value in it is the bot's built-in default, so the bot behaves the same with it or without it: **Railway does not read this file and nothing is pre-added there.** Use it as your list of every setting, with a one-line explanation above each.

- **On Railway:** open the bot service -> **Variables** -> **Raw Editor** and paste *only the lines you want to change* (for example `SITE_RESPECT_ROBOTS=false`). Leave the rest out. Railway redeploys by itself. Only `BOT_TOKEN` is required; `DATABASE_URL`, `REDIS_URL` and `ADMIN_IDS` are strongly recommended.
- **Locally:** put your token in `.env` and run `npm run dev`. `.env` is in `.gitignore` and `.dockerignore`, so it never reaches GitHub or the image.
- **Names are exact and case-sensitive**, and booleans must be lowercase `true` / `false`. Blank means "off / not set".
- **Keeping it in sync:** the list lives in `scripts/env-vars.js`. Run `npm run env` to regenerate `.env`, `.env.example` and the table below. `npm test` fails if the code reads a variable that is not listed, or if a default in `.env` differs from the code.

## Redis vs Postgres
- **Redis (disposable):** result cache, failure cache, per-user lock and cooldown, daily counters, change fingerprints, jobs in flight (for resume).
- **Postgres (durable):** users (language, auto-delete choice), download history, Telegram `file_id`s (so a Redis flush doesn't lose the cache), analytics, admin block list.
- Cached results are shared between users: the bot never sends cookies or credentials, so everyone gets the same public copy. Saved copies are kept for `STALE_MAX_DAYS`; whether one is sent as it is, checked first or rebuilt is decided by the freshness rules below (`RECHECK_AFTER`).
- Privacy: requested URLs are stored with the user's Telegram ID for `RETENTION_DAYS` (default 90), or for the time the person chose in `/privacy`.

## How it works
- **Fast path first:** plain fetch + cheerio. Pages that need JavaScript, look empty, or are refused to a plain request are rendered in Chromium, **per page**. Browser pages are saved as snapshots (scripts removed, so they open with a double-click); plain pages keep their scripts.
- **Retry ladder:** plain fetch -> real browser -> stealthier browser that waits for bot checks to clear. The person sees one result.
- **Sitemap-first discovery** on top of link following, shallow pages first.
- Links are rewritten to relative paths; anything not saved keeps its online URL. `srcset`, lazy-load attributes, CSS `url()`, `@import` and `image-set()` are handled.
- **Before sending:** big images are recompressed if the site would not fit (optional `sharp`), and every local link is checked against what is really in the ZIPs. `_all-pages.html` lists every saved page.
- **Always the latest, decided by the backend** (see *Freshness*): the site is checked before a saved copy is sent; unchanged = the same ZIP at once, changed = rebuilt silently.
- **Resume:** jobs in flight are kept in Redis; after a deploy or crash they continue instead of leaving a dead progress message.
- **Politeness:** per-host request spacing that backs off on 429/503.
- Files over `MAX_FILE_MB` (42), or beyond the ZIP part budget, are skipped and listed in `skipped.txt`.
- Precise failures: not found, protected (even through a real browser), region-blocked, sign-in, DNS, SSL, timeouts, and more, each with a short human message.

## Health and alerts
- **Deploy awareness:** admins get a DM when the bot comes online (version, time, Redis / Postgres / Chromium state, resumed jobs) and when it shuts down. `ADMIN_NOTIFY=false` turns this off. The admin must have started the bot once (`/start`) so Telegram allows it to message them.
- **`/ping`** (admins): Telegram round trip, version, uptime, memory, Redis/Postgres latency, Chromium and queue state.
- **Command menu:** on every start the bot syncs Telegram's menu to the code, removing stale commands in every scope and language.
- `GET /health` (on `$PORT`) returns queue, Redis/Postgres state, browser stats and memory. Set `HEALTH=false` to disable.
- Chromium is recycled when the container uses more than `BROWSER_MEM_RATIO` (0.85) of its memory limit (only while idle).
- Admins get a message when the failure rate of the bot's own jobs spikes, or when Chromium cannot start (at most once an hour per topic).

## Safety and abuse protection
- SSRF protection: private/internal IPs and hostnames blocked, checked on every redirect and every browser request.
- One job per user, cooldown, queue with a waiting cap, size/file/time caps, temp folders deleted after each job.
- `DOMAIN_DAILY_CAP` (new builds of one site per user per day) and `DOMAIN_GLOBAL_DAILY` (all users), `FAIL_STRIKES` / `FAIL_PAUSE_MIN` (a short pause after repeated failed attempts). Sites too big to send are remembered for 6 hours.
- `BLOCKED_DOMAINS` and `/block` stop specific sites (subdomains included).
- Set `ALLOWED_USERS` to restrict the bot to specific Telegram IDs.

## Performance and memory
- **Where the time goes:** `/stats` shows median and 95th-percentile times per phase (fetch, browser, map, crawl, assets, build, zip, upload) over 7 days. Tune what is slow.
- **Downloads** run as one pipeline (stylesheets are expanded as they arrive), 24 files and 8 pages at a time, with an adaptive cap per host (`HOST_MAX_CONCURRENT`) and a stall timeout (`ASSET_STALL_SEC`).
- **Shared asset cache** (`SHARED_CACHE_MB`): pinned CDN libraries and Google Font files are fetched once and reused by every site. Lives on the temp disk and is optional.
- **Repeat requests:** see *Freshness* below.
- **Memory:** Chromium starts on demand and closes after `BROWSER_IDLE_MIN` idle minutes. Extra parallel jobs wait while memory is above `MEM_ADMIT_RATIO` or free disk is under `DISK_MIN_MB`.
- **Observability:** `/ping` (live health), `/stats`, `GET /metrics` (Prometheus text, set `METRICS_TOKEN`), and one structured log line per job (`LOG_FORMAT=json`).

## Freshness, simple for people and smart in the backend
People send a link and get the newest ZIP. They are never asked to choose anything: no "fresh copy", "preview" or "try again" buttons (admins get **Force rebuild / Details / Preview** under their results).
- **`RECHECK_AFTER`** (default `10m`; `30m`, `2h`, `1d`, `7d`, ... or `0` = every time): a saved copy verified more recently than this is sent as it is.
- **Older, or the same person asks again** (asking again soon means "I want it fresh"): the site is checked first, within `RECHECK_TIMEOUT` seconds, with a handful of small requests: the sitemap's last-modified dates, `304 Not Modified` answers and ETags, and a signature of what each page *says* (its visible text and the names of its CSS and JS files, ignoring clocks, tokens and cache-busting noise).
  - **Unchanged:** the same ZIP at once, footer *"✅ Checked just now, nothing changed"*.
  - **Changed:** rebuilt silently and sent. A rebuild because the site changed **costs the person no quota**.
  - **Couldn't check** (slow, unreachable, or a browser-rendered site that cannot be compared): the saved copy with an honest footer *"⚠️ Couldn't check for updates"*; if they ask again, it is rebuilt. Copies that can never be verified are rebuilt after 6 hours or `RECHECK_AFTER`, whichever is longer.
- **Quiet retries:** a site that times out, answers 5xx or rate-limits is retried twice (`RETRY_DELAY_SEC`, then twice as long) before anyone hears about it. Retries are part of the same job and cost no quota.
- **Site gone:** the person gets the last saved copy automatically, as described under Rescue.
- **Exact mirror:** nothing lossy happens to a copy by default. Identical files are stored once; PNG and JPEG are re-packed **losslessly**, and every result is decoded and compared pixel by pixel with the original (anything that differs, or saves under 3%, is dropped; animated and 16-bit PNGs are never touched). JPEG needs `jpegtran` (installed in the Docker image) and everything needs the optional `sharp` package; without them images are simply left as they are. Source code and videos are never touched. `IMAGE_COMPRESS=true` turns the old lossy shrinking back on (admins only, off by default).
- **Left-out media keeps its live address:** a file too big to include, over the ZIP budget or failed to download stays linked to the original, so the opened copy shows it whenever there is internet (it is listed in `skipped.txt`). Embedded players (YouTube, Vimeo, maps) get complete addresses too. A few things no mirror can fix: hotlink-protected files, signed links that expire, and media a script builds at runtime.
- **Sign-in pages:** when pages redirect to a sign-in page, that page is saved **once** in their place, and links to the protected pages open it. The bot never signs in.

## Archive and Ops (three private spaces)
Every successful build is also kept in a private **Live** channel, moved to a private **Vault** channel when its time is up, and reported in a private **Ops** group. When a site later disappears, people are offered the last archived copy.

```
build delivered ──▶ Live channel   preview? + ZIP, labelled and searchable   (same Telegram file: no second upload)
LIVE_RETENTION_HOURS later ──▶ copied to the Vault ──▶ links saved ──▶ only then cleared from Live
site down / blocked / gone ──▶ the archived ZIP is sent to the person automatically, with one plain line
```

**Set up (about five minutes)**
1. Create two **private channels** (Live, Vault) and one **private group** (Ops). In the Ops group turn on **Topics** (Edit -> Topics; choose the **List** layout, it shows each topic's latest message).
2. Send **`/archive setup`** to the bot. Under the message you get one button per space; tap one and **Telegram's own picker** opens, listing only the private channels or groups you administer (Ops shows only groups with Topics on). Choose the chat and it is connected on the spot. No ids to copy.
   - If the bot is not in that chat yet, Telegram adds it as admin with exactly the rights it needs: Live *post, edit and delete messages*; Vault *post messages*; Ops *manage topics*. Nothing else is requested.
   - **Already added the bot earlier?** Same buttons: pick the chat and it is connected. (It does not matter that the bot was added before this version ran.)
   - The message also has two **add-me links** that open Telegram's "add as admin" screen with those rights ticked.
   - Adding the bot to a chat by hand still works: it DMs the admins Live / Vault / Ops buttons.
3. The bot checks the chat kind and its own rights and says exactly what is missing; the keyboard shrinks as spaces get connected, and Ops gets its six topics automatically.
4. Send `/archive test`: it writes to the database, posts to and deletes from each channel, copies Live -> Vault, creates the topics and posts to Ops, then reports each step. All green means it works in your setup. If a space is missing it says so and points you to `/archive setup`; the online message at startup does the same.
Prefer variables? `LIVE_CHANNEL_ID`, `VAULT_CHANNEL_ID`, `OPS_CHAT_ID` override the buttons.

**What a Live post looks like**
```
📦 example.com
Page title
🗓 Oct 10, 2026 · 21:03 UTC
📄 12 pages · 🗂 80 files · 💾 5.0 MB
⏳ Live until Oct 17

#example_com #2026_10 #id_a3f9c2 #site
```
With a preview picture the picture carries this label and the ZIP is a reply to it; without one the first ZIP carries it. Several ZIPs: *Part 2 of 3* as replies. Tags make everything searchable inside Telegram (`#example_com`, `#2026_10`, `#id_...`, `#dynamic`, `#files`). A **preview picture** is added only when one already exists (the browser rendered the page anyway, or someone asked for a preview): the archive never starts a browser just for a picture.

**Lifecycle and safety**
- Everything goes through a durable **outbox** (Postgres): restarts lose nothing, failures retry with backoff, Telegram's 429 "wait N seconds" is honoured, and posting can never delay or break someone's download. Posts are paced to `ARCHIVE_RATE_PER_MIN` per channel.
- **Order is the safety:** at expiry the Vault copy and its links are saved *before* anything is deleted from Live. If the Vault copy fails, the Live post stays and Ops alerts you (`/archive retry` after fixing the cause). A Live post deleted by hand is rebuilt in the Vault from the saved files.
- Items **stay in the Vault forever**; the bot keeps their links (no user data) so `/archive example.com` can find them and rescue can use them.
- **Rescue:** when a site is not found, down, blocked, timing out and so on, the person simply receives the last saved copy (from the cache, else the archive) with one plain line: *"This site isn't reachable right now. Here's the latest copy I saved, from Oct 3."* No button to find. If the Telegram file reference has expired, the ZIP is copied straight from the Live or Vault post.
- **Privacy:** posts and the stored records contain no user id, name or username, and the tables have no user column, so *Delete all my data* never touches the archive. Ops shows only a short hashed tag (`user #a3f9`) that cannot be turned back into an id.
- Without Postgres the archive still works but keeps its records in memory only (lost on restart); `/archive` says so.

## Zero-downtime deploys (webhook mode)
By default the bot long-polls, which leaves a short gap while a new version starts. To remove it:
1. Give the bot service a public domain on Railway (Settings -> Networking -> Generate Domain) and make sure it listens on `$PORT` (it does).
2. Set `WEBHOOK_DOMAIN=your-service.up.railway.app` (no `https://`) and redeploy.
3. On start the bot checks that the address answers, then registers the webhook (secret path and secret token are derived from your bot token). If the address is unreachable it falls back to polling and tells admins.
4. Pending updates are kept during a deploy, so nothing sent while the new version starts is lost. On shutdown the bot stops taking calls, lets running jobs finish for `DRAIN_SECONDS`, and leaves the rest to resume.
To go back to polling, unset `WEBHOOK_DOMAIN`.

## Bigger files: self-hosted Telegram Bot API (optional)
Telegram's cloud API caps uploads at 50 MB. A self-hosted Bot API server raises that to 2 GB, so big sites arrive as one or a few ZIPs.
1. Add a Railway service from the image `aiogram/telegram-bot-api` with `TELEGRAM_API_ID` and `TELEGRAM_API_HASH` (from https://my.telegram.org). Keep it on the private network.
2. **Once**, log the bot out of the cloud API: open `https://api.telegram.org/bot<TOKEN>/logOut` in a browser.
3. Set `TELEGRAM_API_URL=http://<that-service>.railway.internal:8081` on the bot and redeploy.
Defaults adapt automatically: 1.5 GB ZIP parts, 150 MB single files, 1.2 GB per site (override with `PART_MB`, `MAX_FILE_MB`, `SITE_MAX_TOTAL_MB`). Files are held in memory while downloading, so keep `MAX_FILE_MB` modest on small instances.

## Admins
There is no admin screen. An admin is a Telegram user ID listed in the `ADMIN_IDS` variable.
1. Send `/myid` to the bot to get your ID.
2. Set `ADMIN_IDS=<your id>` (comma-separate several) and redeploy.
3. Admins get `/stats`, `/ban`, `/unban`, `/block`, `/unblock` in their command menu, and are exempt from the cooldown, the one-at-a-time lock, `DAILY_LIMIT`, domain caps, bans and `ALLOWED_USERS`. Admins cannot be banned.

## Whole-site crawl (the default for every link)
- `example.com` saves the whole site. `example.com/docs` saves that part of the site only.
- **Pages:** same host, breadth-first, up to `SITE_MAX_PAGES` (300) and `SITE_DEPTH` (10); sites that build pages with JavaScript are capped at `SITE_MAX_PAGES_BROWSER` (60). Disallowed paths in `robots.txt` are skipped (`SITE_RESPECT_ROBOTS=false` turns that off). Links with `?query` are not followed. Pages that redirect to a sign-in are left out.
- **ZIP parts:** about `PART_MB` (48) MB each, filled using the real compressed sizes, at most `SITE_MAX_PARTS` (12). Every path is relative to one shared root, so unzipping all parts into the same folder gives a working site. Part 1 holds `index.html`, `README.txt`, `_all-pages.html` and `skipped.txt`. With several parts the bot first sends a summary message, then *Part i of n*.
- **When it does not fit:** images are recompressed first; then code and pages are packed first and the largest videos/images/documents are left out (listed in `skipped.txt`, still loading from the live site online).
- **Folder listings:** an "Index of" page is detected automatically and downloaded as files (`SITE_MAX_FILES`, `SITE_MAX_DIRS`, `SITE_MAX_TOTAL_MB`), keeping the folder structure.
- Time limit `SITE_TIMEOUT_SEC` (480). One link counts as one download toward `DAILY_LIMIT`.

## Message style
All messages are Telegram HTML built from one small vocabulary in `src/fmt.js` (bold titles, `monospace` values, italic hints, 🟢🟡🔴 health dots). Anything from outside is escaped with `esc()`. If Telegram rejects a message's formatting, it is resent as plain text. `npm test` validates every message in every language.

## Editing the wording
Everything users read is in `src/copy.js` (English: start text, progress, captions, notes, errors, small messages, buttons), `src/locales/*.js` (translations; any missing key falls back to English), `src/help.js` (the /help guides, English) and `src/profile.js` (the bot's Telegram description). The backend keeps precise error codes and technical details in logs and the database, so you can reword freely. To add a language: create `src/locales/xx.js`, register it in `src/locales/index.js` and `LANGS` in `copy.js`; `npm test` checks the keys.
